# Business Workflow Map

This map defines handoffs between module owners, not a distributed transaction. Each producer commits its own record and an outbox event atomically. Consumers deduplicate, validate their own preconditions, and either acknowledge or expose a retry/reconciliation case. A consumer never edits the producer's records. Module 04 records approvals; the business owner applies the resulting decision to its own record. Module 24 delivers notifications and does not change source state.

## Shared event contract

Events carry `event_id`, `event_type`, `schema_version`, UTC occurrence time, producer, entity ID, actor/scope reference where permitted, correlation and causation IDs, and only the payload needed by consumers. Outbox writes occur in the same database transaction as the producer's state change. Consumers persist dedupe keys and processing outcome. Notifications are derived from approved domain/workflow events; they are not approval records.

## Cross-cutting recovery

Classify failures as validation/business rejection, transient transport failure, or ambiguous external outcome. Correctable business failures return to the owning module for correction. Retry transport only when idempotent. Ambiguous financial outcomes enter reconciliation, not blind retry. Dead-letter/reconciliation queues retain correlation and source references, redact secrets, and expose an accountable owner. No cross-module process claims global atomicity across separate commits.
